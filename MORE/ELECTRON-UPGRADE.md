# Electron upgrade

Move `electron-app` from Electron 37.6.0 to 45.3.4, clear the vulnerabilities that come with the old
version, and introduce a `node:sqlite` implementation behind `sqlio` so that the native module can eventually
go. `vscode-ext` is expected to break and is not repaired here.

Written to be reviewed before the work starts. Delete it when the work is done.

## Why now

- Electron 37.6.0 is well behind — 45.3.4 is current — and the old version is where most of the audit findings
  will be.
- `sqlio` exists to wrap `better-sqlite3`, whose binding must be rebuilt for every host and every ABI. That is
  the constraint `CONSTRAINTS.md` records, and it is the reason `vscode-ext` cannot share an Electron version
  with `electron-app`.
- `node:sqlite` is built into Node, and Electron 37.6 already exposes it with an experimental warning. If
  `sqlio` can sit on it, the native module and the whole rebuild problem go away — for the app and, later, for
  the extension.

## Three checks before anything is installed

1. **Which Node does Electron 45.3.4 bundle?** It decides whether `.nvmrc` and the `@types/node` override
   move. `node:sqlite` is stable in newer Node and experimental in older; the warning in the current version
   suggests it is still the latter, but the bundled version should be read rather than assumed.
2. **Does `@electron-forge` support Electron 45?** Forge 8 is what builds the app, and a major Electron jump
   can outrun it. Worth checking its supported range before committing to the upgrade, since a Forge bump is a
   much larger piece of work than this plan assumes.
3. **Does the packaging still work?** `ResourcePlugin` copies `Core.exe` and the Forge config names it as
   `extraResource`. Nothing here should touch that, but a Forge or Electron change is exactly what breaks it,
   and `package` is the only command that exercises it.

## Repo files to edit

Before the rebuild, and before the retest:

| file                                 | what changes                                                                                                |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `package.json` (root)                | `overrides.electron` to 45.3.4; `overrides.@types/node` if Node moves; `overrides.shell-quote` to `^1.12.0` |
| `packages/electron-app/package.json` | the `electron` devDependency; any `@electron-forge/*` that must follow                                      |
| `packages/sqlio/package.json`        | the `rebuild` script's hard-coded `-v 37.6.0`                                                               |
| `.nvmrc`                             | only if the bundled Node moves                                                                              |
| `packages/vscode-ext/package.json`   | nothing yet — it is expected to break, and is dealt with later                                              |
| `docs/architecture/CONSTRAINTS.md`   | Tech stack; the ABI rule; Known limitations                                                                 |
| `docs/architecture/TESTING.md`       | the `electron-rebuild -v` line                                                                              |
| `docs/architecture/PACKAGES.md`      | the `sqlio` entry, which states its obsolescence                                                            |

Worth checking, but probably nothing: `.github/dependabot.yml` and `.vscode/launch.json`, in case either
names an Electron version.

The lockfile is regenerated by npm, not edited.

## Steps

1. Edit the four version-bearing files above — root `overrides`, `electron-app`'s dependency, `sqlio`'s
   `rebuild` script, and `.nvmrc` if Node moves.
2. `npm install` at the root, so one Electron is resolved for the workspace.
3. `npm run type-check -w apis` — cheap, and it catches a types-level break before anything is rebuilt.
4. `npm run rebuild -w sqlio`, now against the new Electron.
5. `npm test -w backend-test` — it runs under Electron, so it exercises the new ABI and the rebuilt binding
   together. This is the first real test of the upgrade.
6. `npm start -w apis` — the app opens, a data source loads, a view renders.
7. `npm run package -w apis` — the step that exercises `ResourcePlugin` and `Core.exe`.
8. `npm audit` at the root, and again in `electron-app`. Whatever is left after the bump is the real list —
   and `shell-quote` is the one finding the bump cannot fix, since it comes down Forge's dev-server tree
   rather than Electron's. It is the only critical, it is `dev`-only, and it clears with the override above.
9. Update the three documents in the same commit as the versions.

## Phase 2 — the `node:sqlite` shim

Only once the upgrade is verified, and only if the app is working on the new Electron.

`sqlio`'s surface is three exports — `createSqlDatabase`, `SqlDatabase`, `SqlTable` — with the native binding's
path as a _parameter_, which a shim can ignore. That is what makes this feasible at all.

What differs, and where the work is:

- `node:sqlite` gives `DatabaseSync` and `StatementSync`; there is no `.transaction()` helper, and pragma
  handling is not identical. `sqlDatabase.ts` and `sqlTable.ts` are the two files to read first.
- `packages/backend-test/test/sqlio.test.ts` calls `createSqlDatabase(fileTempDb, fileNativeSqlite)`. The shim
  must accept and ignore that second argument, or the test needs a variant — decide which before writing it,
  since that test is what proves the shim works.
- `paths.ts` throws if the native binding is missing, so the test helpers need to tolerate its absence under
  the shim.

Then regression-test with `electron-app`: load a model, expand nodes, use a popup, reopen a data source.

## Out of scope

- **`vscode-ext`.** It will fail at activation with a `NODE_MODULE_VERSION` mismatch, because the extension
  runs in VS Code's own Electron and not the app's. Its ABI is VS Code's to match, and it is dealt with when
  that package is next worked on — not here.
- **.NET.** `Core.exe` runs on its own runtime and is untouched by any of this.
- **TypeScript.** Pinned to 5.9.2 in the overrides; a compiler upgrade is its own piece of work.

## Verification

The upgrade is done when:

- `npm run type-check -w apis` passes
- `npm test -w backend-test` passes against the rebuilt binding
- `npm start -w apis` runs, loads a model and draws a view
- `npm run package -w apis` produces an app that still finds `Core.exe`
- `npm audit` reports nothing that the bump could have fixed
- `CONSTRAINTS.md`, `TESTING.md` and `PACKAGES.md` name the new versions
